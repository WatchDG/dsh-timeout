# dsh-timeout

[![CI](https://github.com/WatchDG/dsh-timeout/actions/workflows/ci.yml/badge.svg)](https://github.com/WatchDG/dsh-timeout/actions/workflows/ci.yml)
[![License: Apache-2.0](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

[English](README.md) | **Русский**

Стратегия повторных попыток с экспоненциальной задержкой (exponential backoff)
для [DeepSeek Harness](https://www.deepseek.com/en/harness/). DSH запускает
вызов инструмента один раз: если он упал — или упёрся в таймаут, — ошибка
сразу попадает модели, и модель вынуждена повторять вызов вручную. Этот плагин
оборачивает водопад `tools/execute` и повторяет настроенные сбои с
настраиваемой экспоненциальной задержкой:

```
delay = min(maxTimeoutMs, minTimeoutMs × factor^(попытка − 1))
```

пока вызов не пройдёт, не кончится бюджет попыток или вызывающая сторона не
отменит его. Вместо встроенной одиночной попытки с таймаутом вы получаете
контролируемую стратегию — без перезапуска, настройки меняются вживую.

## Требования

| Требование | Детали |
|---|---|
| [DeepSeek Harness](https://www.deepseek.com/en/harness/) | 0.2.2-RC.1 (проверено; также 0.2.1-RC.5). Плагин использует сервис `tools` и событие `tools/execute`. |
| Node.js | 24.9 или новее; DSH 0.2.2 поднимает минимальную версию Node.js до 24.9. |

Внешние бинарники не нужны, шага сборки нет.

## Установка в DeepSeek Harness

Плагин — это бандл профиля DSH, поэтому он действует на все сессии этого
профиля.

1. Откройте страницу **Plugins** в боковой панели DSH (Plugin Manager).
2. Нажмите **Add plugin** / **Install bundle**, выберите этот каталог
   (тот, где лежит `package.json`), и подтвердите.
3. Убедитесь, что **Экспоненциальный бэкoфф** включён в списке плагинов.

Тот же шаг доступен агенту через инструмент `plugin_manager` с
`action: install_bundle` и абсолютным путём к каталогу. DSH записывает в
`package.json` профиля зависимость `link:` на каталог; поскольку каталог
связан, после обновления файлов плагина перезапустите DSH, чтобы Host
загрузил новый JavaScript.

Удаление — через Plugin Manager (или `plugin_manager` с
`action: remove_bundle`).

## Что делает плагин

### Цикл повторов с экспоненциальной задержкой

Слушатель `tools/execute` выполняет вызов и повторяет настроенные сбои для того
же идентификатора вызова (те же имя, аргументы, агент и сигнал). Первая попытка
вызывает `next()` водопада ровно один раз и выполняет остаток цепочки. В DSH
0.2.2 поставляется Cordis 4.1.0, где `next()` одноразовый — повторный вызов
бросает `next() called multiple times`, — поэтому повтор идёт в обход водопада:
тело инструмента запускается напрямую через найденный `ToolDefinition`
(`ctx.tools.executable(name, agent, exec.toolSet)`, с запасным
`ctx.tools.get(name, agent)`), а реестр заново нормализует сырое значение через
контракт вывода инструмента. Поэтому повторные попытки сохраняют исходный
идентификатор вызова, единственный гейт `tools/pre-execute` и его подтверждения
проходят один раз, а единственный проход `tools/post-execute` / `tools/result`
по-прежнему случается один раз после возврата обёртки. После каждой упавшей
повторяемой попытки следует ожидание `minTimeoutMs × factor^(попытка − 1)`
(не больше `maxTimeoutMs`), затем начинается следующая попытка.

Детали поведения:

- **Попытки** — всего `maxAttempts` попыток на вызов (по умолчанию 3) либо без
  ограничений при флаге `unlimited`. Ожидание растёт до `maxTimeoutMs`, так что
  вечно падающий вызов будет повторяться с потолком задержки.
- **Что повторяется** — только сбои, чей структурированный код ошибки есть в
  `codes` (по умолчанию `TOOL_TIMEOUT`). Звёздочка `*` повторяет любую ошибку.
  Вызов без структурированного кода не повторяется, пока не настроен `*`.
- **Джиттер** — задержки повторов случайно «размазываются», чтобы параллельные
  вызовы (DSH запускает до нескольких подадач одновременно) не били сервис
  синхронно: `none` — фиксированное расписание, `equal` (по умолчанию) —
  разброс ±`jitterRatio` вокруг базовой, `full` — равномерно из `0..base`.
- **Переопределения по инструментам** — `toolOverrides` позволяет переопределить
  любую настройку повторов для конкретного инструмента; незаполненные поля
  наследуют глобальные значения.
- **Отмена главенствует** — если сигнал вызывающей стороны прерывает ожидание,
  повторы прекращаются и возвращается последний сбой. Вызов, чей вызывающий уже
  отменён, никогда не повторяется.
- **Исчерпание** — когда бюджет кончился, возвращается последний сбой без
  изменений, и модель видит настоящую ошибку.
- **Без повторных подтверждений** — проверки перед выполнением, гарды и
  подтверждения проходят один раз до цикла; `tools/post-execute` и
  `tools/result` — один раз после него.
- **Дурабельные события сессии** — каждый запланированный повтор добавляет в лог
  сессии `tool/retry` (`callId`, `tool`, `attempt`, `code`, `delayMs`) и
  `tool/retry-started`, поэтому повторы видны в истории сессии и анализируемы
  по сессиям.

### Таймаут на каждую попытку

Встроенное принудительное применение таймаутов в DSH — отдельный пакет, который
профиль может не содержать; при этом инструменты объявляют `timeoutMs`. При
`armTimeout` (по умолчанию включён) плагин ставит объявленный таймаут **на
каждую попытку**: у каждой попытки свой бюджет, и зависший вызов превращается в
повторяемый `TOOL_TIMEOUT`, а не в зависшую отправку. Именно это делает повторы
полезными для по-настоящему медленных или временно недоступных операций.

### Страница настроек

**Settings → Бэкoфф** показывает:

- **Живые счётчики** — попытки инструментов, их повторы, срабатывания
  таймаута и последний код инструмента, а также запросы к модели, повторы
  модели и последний код модели с момента загрузки плагина хостом
  (`GET /backoff/status`). Пока раздел открыт, счётчики перечитывают маршрут,
  поэтому повторы, случившиеся после открытия страницы, видны без нажатия
  **Обновить**.
- **Активность по сессиям** — те же счётчики инструментов *и* модели в разбивке
  по сессиям, сначала самые активные.
- **Поведение** — конфигурацию ниже, редактируемую на месте без перезапуска
  через volatile-поля, включая джиттер и переопределения по инструментам.

## Настройка

Все поля необязательны. Переопределите строку `backoff` в патче профиля или
меняйте вживую на странице **Settings → Бэкoфф**.

| Поле | Тип | По умолчанию | Значение |
|---|---|---|---|
| `enabled` | boolean | `true` | общий рубильник; выкл = один запуск, как в DSH по умолчанию |
| `maxAttempts` | number | `3` | всего попыток на вызов (включая первую). Игнорируется при `unlimited` |
| `unlimited` | boolean | `false` | повторять до успеха или прерывания вызывающим |
| `minTimeoutMs` | number | `1000` | задержка первой повторной попытки, мс |
| `maxTimeoutMs` | number | `60000` | потолок задержки, мс; значение меньше `minTimeoutMs` поднимается до него |
| `factor` | number | `2` | множитель роста задержки с каждой попыткой (> 1) |
| `codes` | string[] | `['TOOL_TIMEOUT']` | коды ошибок, вызывающие повтор; `["*"]` — любая ошибка |
| `tools` | string[] | `[]` | имена инструментов; пусто — все инструменты |
| `armTimeout` | boolean | `true` | применять объявленный `timeoutMs` инструмента как таймаут попытки |
| `jitter` | `'none' \| 'equal' \| 'full'` | `'equal'` | случайность задержки: фикс., ±ratio вокруг базовой или равномерно 0..base |
| `jitterRatio` | number | `0.5` | разброс для `equal`-джиттера (±50 %) |
| `toolOverrides` | object | `{}` | частичные переопределения по инструментам; незаполненные поля наследуют глобальные |
| `llmEnabled` | boolean | `false` | повторять запросы к модели (`Retried model request` в чате) |
| `llmUnlimited` | boolean | `false` | неограниченные повторы модели (`retry/∞`) |
| `llmMaxRetries` | number | `10` | повторы модели после первого сбоя; игнорируется при `llmUnlimited` |
| `llmMinTimeoutMs` | number | `1000` | задержка первого повтора модели |
| `llmMaxTimeoutMs` | number | `30000` | потолок задержки модели; `Retry-After` провайдера в его пределах выигрывает |
| `llmFactor` | number | `2` | множитель роста задержки модели |
| `llmCodes` | string[] | `[EMPTY_RESPONSE,RATE_LIMIT,SERVER,TIMEOUT,TRANSPORT]` | коды модели для повтора; `["*"]` — любой |
| `llmJitter` | `'none' \| 'equal' \| 'full'` | `'equal'` | случайность задержки модели |
| `llmJitterRatio` | number | `0.2` | разброс для `equal`-джиттера модели (±20 %) |

```yaml
- id: backoff
  config:
    enabled: true
    maxAttempts: 5          # до 5 попыток на вызов
    unlimited: false
    minTimeoutMs: 500       # первый повтор через 0.5 с
    maxTimeoutMs: 30000     # не ждать дольше 30 с
    factor: 2               # 0.5с → 1с → 2с → 4с → …
    codes: [TOOL_TIMEOUT]  # повторять только таймауты
    tools: [pwsh, bash]     # только shell-инструменты
    armTimeout: true
    jitter: equal           # ±50% вокруг базовой (jitterRatio 0.5)
    jitterRatio: 0.5
    toolOverrides:          # переопределения по инструментам
      pwsh:
        maxAttempts: 3      # меньше попыток для шеллов
        codes: [TOOL_TIMEOUT, COMMAND_FAILED]
      web_fetch:
        unlimited: true     # повторять загрузки до успеха
    llmEnabled: true        # повторять Connection error (TRANSPORT) и т.п.
    llmMaxRetries: 10
    llmUnlimited: false     # true = retry/∞ до успеха или прерывания
    llmMinTimeoutMs: 1000
    llmMaxTimeoutMs: 30000
    llmCodes: [EMPTY_RESPONSE, RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT]
```

### Запросы к модели (`Retried model request`)

Инструменты и модель полностью независимы: инструменты —
`enabled/maxAttempts/unlimited/...`, модель —
`llmEnabled/llmMaxRetries/llmUnlimited/...`. Отключение инструментов не
останавливает повторы модели и наоборот.

`Retried model request (retry/maximum)` — это встроенный исполнитель
`dsh-llm-retry` плюс `retryPolicy` каждого провайдера (по умолчанию: 5 повторов
для `EMPTY_RESPONSE,RATE_LIMIT,SERVER,TIMEOUT,TRANSPORT`). `Connection error` —
это `TRANSPORT`, так что 5 повторов, а затем `This turn failed` — ожидаемое
поведение по умолчанию.

Плагин добавляет собственный слушатель `agent/request-error` при включённом
`llmEnabled`, испуская те же события `llm/retry`, поэтому чат рендерит их так же
(`retry/∞` при `llmUnlimited`). Его учёт цепочки повторов хранится в памяти
процесса и по сессиям, сбрасывается при новом turn/step (исчерпанный бюджет
никогда не глушит более поздние сбои); дурабельны в логе сессии только события
`llm/retry` / `llm/retry-started`. Суммы складываются, когда включены оба
исполнителя (встроенный + этот плагин); чтобы считать только этот плагин,
отключите встроенный маршрут:

```yaml
- id: llm-pi-ai
  config:
    providers:
      opencode-go:
        retryPolicy: { mode: normal, maxRetries: 0 }
```

## Замечания по безопасности

- Повторные попытки запускают **тот же вызов с теми же аргументами**. Для
  инструментов с побочными эффектами (запись файлов, изменения в сети) решите,
  безопасно ли повторное выполнение; сузьте `codes`/`tools` или поднимайте
  `maxAttempts` только там, где это безопасно.
- По умолчанию повторяются **только таймауты** (`TOOL_TIMEOUT`) — классический
  случай, где повтор безвреден.
- Плагин не ходит в сеть и не запускает процессы: он только управляет
  существующим конвейером выполнения инструментов. Страница настроек
  обращается к собственному аутентифицированному роуту хоста `/backoff/status`.

## Проверка

1. На странице **Plugins** есть **Экспоненциальный бэкoфф**, плагин включён.
2. **Settings → Бэкoфф** показывает живые счётчики и редактируемую форму.
3. В сессии выполните команду, которая зависает дольше `timeoutMs` инструмента
   (или намеренно падающий вызов с `codes: ["*"]`): в логе и счётчиках будут
   повторы, а итоговый результат придёт после настроенного паттерна задержек.
4. Проверьте, что отменённый вызов немедленно прекращает повторы.

## Устранение неполадок

| Симптом | Причина / решение |
|---|---|
| Ничего не повторяется | Плагин выключен, инструмента нет в `tools` или кода сбоя нет в `codes`. |
| Зависший вызов всё ещё зависает | `armTimeout` выключен или инструмент не объявляет `timeoutMs` (нечего ставить). |
| Слишком много повторов | Уменьшите `maxAttempts`, уберите `*` из `codes` или включайте `unlimited` осознанно. |
| Страница настроек «не отдаёт конфигурацию» | Профиль хранит настройки только для чтения или изменился id строки `backoff`. |

## Разработка

Одна зависимость (`@deepseek-ai/schemastery` для схемы настроек), шага сборки
нет.

```bash
npm install            # установить зависимости (схема настроек + Cordis для контрактных тестов)
npm test               # юнит-тесты, контрактные тесты и проверка манифеста
npm run test:unit      # те же наборы
npm run pack:check     # проверить состав npm-пакета
```

Структура:

```
index.js              точка входа Host: экспортирует apply / name / inject / Config
client.js             страница Settings → Бэкoфф: счётчики и форма поведения (веб-клиент)
lib/config.js         схема Config, значения по умолчанию, нормализация, живой снапшот
lib/backoff.js        чистая математика стратегии: задержки, классификация повторов, дедлайн
lib/plugin.js         подключение к контексту (namespace настроек + цикл повторов tools/execute + роут статуса)
test/                 наборы node:test (config, backoff, llm, plugin, client, contract, manifest)
```

Если добавляете runtime-модуль, добавьте его в `files` в `package.json`;
иначе тест манифеста упадёт. См. [CONTRIBUTING.md](CONTRIBUTING.md).
